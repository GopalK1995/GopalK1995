T042 · Gmail + Google Calendar · MERGED (sha in final message)
Done:
- Two connectors, `google-calendar` and `gmail`, under src/lib/connectors/google/{calendar,gmail}/**, registered in connectors/all.ts. Same Google OAuth client and env names as T039 (PKCE, offline access, tokens in the Vault). Per-user OAuth: the framework keeps one connection per workspace and connector, so each user's own grant lives in the connection's Vault bundle (first user at the top level, others as `grant:<uid>`); `refresh` renews every grant, a dead primary grant is a CredentialError (needs_attention, reconnect), another user's dead grant is marked and skipped.
- Calendar (sensitive scope `calendar.events`): `pull` stream per connected user (Google sync token, window of -30/+365 days first, HTTP 410 restarts the window, cancellations applied) and `push` stream. Only CRM-related events are stored: stamped by the CRM (`crm_kind`, `crm_object_type`, `crm_object_id` private properties) or with a known lead/contact attendee; private/confidential and unrelated events are ignored and never copied. Last write wins (a local edit newer than Google's copy is kept and pushed; equal content is a no-op, so no echo). Demos, meetings and hospitality room holds (tentative, linked to a custom object) go out to Google and map back; `createCalendarEvent` is the server-action target.
- Gmail (RESTRICTED `gmail.readonly` + `gmail.send`): open only when the Google app is in testing (`GOOGLE_OAUTH_APP_MODE=testing`) or CASA is complete, AND the tenant opted in (two acknowledgements, audited `gmail.opt_in`). While closed `gmailScopes` returns none, the connector is not_configured without the app-mode env, and the stream and `sendGmailReply` refuse without the opt-in stamp. Reads threads only with known contacts: Google searches in chunks of known addresses (strangers' mail is not listed), and the thread matcher keeps a thread only when a known contact is the sender or a direct recipient (Cc-only, bulk and unknown threads dropped, never stored). Kept threads become `conversations` (channel email) + `messages`. Replies go from the acting user's own mailbox into a thread of the same workspace whose contact is a participant; audit before send, ids only.
- Tenant isolation: connection lookups check tenant and workspace (a foreign id is "not found"); every store call is scoped by tenant_id and workspace_id; contact lookups see the connection's workspace only. Audit: `google.user_connected`, `gcal.event_created`, `gmail.opt_in`, `gmail.reply_sent` (plus core connect/disconnect).
- Showcase: mock gateways (sandbox token `google-mock-token` or APP_ENV=demo), no network, refused in production; Showcase Gmail reads nothing. Strings: namespace `gmail` (en, ta placeholder) registered in src/i18n/registry.ts; `google-calendar.sandbox`, `gmail.sandbox` in integrations.json. Env names in .env.example, no values.
Tests: unit src/lib/connectors/google/{calendar,gmail}/__tests__ (mapper fixtures incl. all-day holds and zones, last-write-wins, pull/push through fakes incl. sync tokens, 410, echo, backlog paging, tenant scoping, grants and token expiry through the real core, thread matcher fixtures, gate, gated start, closed-gate sync, reply, hard-rule scan). Cypress written, NOT run: connectors/gcal-sync.cy.ts, connectors/gmail-gated.cy.ts. typecheck, lint and Vitest only; no build, no browser.
Deviations from plan:
- No UI (not in Owns): connect, gate panel, grant list and reply box are server-action targets plus `gmailGate` and i18n strings.
- The generic OAuth routes keep one grant per connection and do not know the Gmail gate: callback and start must call `connectGoogleUser` / `startGmailConnect` (see "T042 needs"). The runtime gate holds even without that wiring.
- Opt-in is persisted as a stamp in the credential bundle at connect (no tenant-level column exists); before connecting it is the audited call to `startGmailConnect`.
- PATCH is sent as POST + `X-HTTP-Method-Override` because the shared Google helper (T039) speaks GET and POST only.
Needs from integrator: see "T042 needs" in docs/migrations-backlog.md (catalogue + availability SQL, callback/start wiring, server actions, redirect URIs, env).
Owner decisions: Google OAuth app verification for the sensitive scopes (calendar, gmail.send); CASA assessment for gmail.readonly (until then Gmail is named test users only, max 100, 7-day refresh-token expiry in testing); whether Gmail should ever read more than known-contact threads (needs CASA and a privacy review); whether non-CRM calendar events should ever be imported (off by design).
Known gaps: nothing ran against real Supabase, Vault, Google or a browser. Supabase stores are not unit-tested (fakes only); lead/contact email lookups are exact-case on stored emails. Attendee-to-contact linking takes the first match. Push only writes to the primary user's calendar for unlinked CRM rows. All-day events use the event or calendar time zone via Intl (DST edge at midnight not special-cased).

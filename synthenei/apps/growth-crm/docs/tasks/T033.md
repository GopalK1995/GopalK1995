Done:
- Custom objects at `/settings/objects` (objects.manage): create with labels en and ta (singular and plural), an icon from an allow-list of 17, and a primary field label. The key is derived from the English singular label (shown before saving, immutable afterwards, system words are reserved and get an `x_` prefix). Creating inserts the `object_types` row (kind custom) and its required, searchable text primary field, then audits (`objects.created`) and emits `metadata.changed`. Edit labels and icon, enable and disable (disable hides the object and keeps its records). Org policy `allow_custom_objects` is checked first and explained. The DB trigger from 0017 creates `obj:<key>.read|write|delete` and gives owner full and sales manager read+write; nothing in the code names a role.
- Generic list `/o/<key>`: tanstack table (DataTableV2), columns from the viewer's list layout (or the saved view), filter bar built from field_defs (select, multi select, yes/no) plus search, a sort control, URL-driven so a link is a view. Saved views (`saved_views`): save current filters, sort and columns; private always, team or workspace only with `views.share` (also RLS); rename, re-share and delete by the owner or a views.share holder; retired fields are dropped on load. Real sessions read `records` through RLS (soft-deleted rows excluded, 200 rows, 1000 when an operator needs the in-memory pass), then filters, sort and PII masks run server-side before props are serialised.
- Detail `/o/<key>/<id>`: title with inline rename (writes `title` and the primary field together under the record version), delete (soft, `deleted_at`, needs obj:<key>.delete), layout sections rendered through T030's `CustomFieldsPanel` (sections and field order come from the layout, one panel so one version), related records through `record_links` (add by title search needs write on this record and read on the target, remove needs write; titles of linked custom records are masked when the viewer cannot see that object's primary field; links to system records show type only), comments, follow and activity from T027 `RecordCollab` with object type `obj:<key>`.
- Layouts at `/settings/layouts` (layouts.manage): per object, kind (record page or list), scope (all workspaces or this workspace) and optional role. Precedence workspace+role, org+role, workspace, org, then a generated default; any layout failure falls back to the default. Editor: sections with titles, fields placed, moved and removed with buttons, related and comments switches; list columns. Strict validation on save (unknown, retired, duplicate and primary fields refused), version-guarded write (`layouts.version`), "Remove this layout" falls back to the next broader one. Audit `layouts.saved|deleted`, `metadata.changed`.
- Permissions: page and action checks use `obj:<key>.*` through the engine (`can`, `assertCan`), `fields.manage`, `views.share`; read-only support sessions cannot write. The role editor (Roles and access) lists each object's three permissions after the catalogue, in the editor and in the explain picker, with no code change per object.
- Nav: `Records` group (enabled objects the viewer may read, resolved on the server, icon from the allow-list) between the work groups and Admin; Admin gains Custom fields, Custom objects and Layouts, each gated by its permission.
- Audit and concurrency: records write `records.created|updated|deleted|linked|unlinked` explicitly (no DB audit trigger on `records` yet; ids and keys only, never values); record writes use `updateVersioned` (stale = conflict with only the current version), objects use `updated_at`, layouts use `version`. Audit failures are shown in the result, never hidden.
- Demo: one labelled example object `example_items` (Example item(s), six fields incl. a PII phone, four records, one shared view, one role layout for sales reps, one link). Demo grants mirror the DB defaults (owner full, sales manager read and write, sales rep read); every write validates and answers "Demo workspace: nothing was saved", no Supabase client is created.
- i18n: `messages/{en,ta}/objects.json` registered in `src/i18n/registry.ts` (`objects`); Tamil is a partial draft flagged in `messages/ta/_review.json` (keys also in `messages/ta/_review/objects.json`). Object nouns come from the object's own labels (ta when the viewer's language is Tamil and a Tamil label exists), vocabulary nouns for system objects. Nothing tenant, brand, price or URL specific is hardcoded (a unit test checks the demo data).

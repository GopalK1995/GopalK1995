T038 · Email outbound (Resend / SMTP) + Mailchimp · MERGED (sha in final message)
Done:
- Connectors `resend` (tenant's own Resend account) and `email-smtp` (tenant's own mail server), plus `mailchimp` (OAuth), registered in connectors/all.ts. Credentials go through the generic connect form, are verified with one call and stored encrypted by the framework lifecycle. Gmail restricted scopes are not used for sending.
- Sender identity (name, address, reply-to, footer, DKIM selector) is per connection and lives in `integrations.settings`, edited on /settings/email. Nothing is defaulted in code; with no sender set every send is blocked as `no_sender`. The platform default sender (EMAIL_FROM / EMAIL_REPLY_TO / RESEND_API_KEY, env names only) exists only for system mail (`platform.ts`), never for a tenant's marketing mail.
- Domain verification: Resend answers from its API (SPF/DKIM records and status, shown as returned); SMTP is checked by DNS lookup ("found", not "authorised"; DKIM needs the tenant's selector). Statuses are verified / pending / failed / not started / unknown / showcase. The sandbox says Showcase, an unreachable provider says Unknown, nothing is reported verified without evidence. Re-checked every 6 h and on "Check now".
- Send pipeline (send.ts), every gate fails closed and is recorded: sender -> address -> `can_contact(marketing_email)` (re-checked at send time for queued rows, a throw means nothing is sent) -> suppression list -> merge fields (HTML-escaped; a missing field blocks the message by name instead of sending a blank) -> unsubscribe link (no secret or base URL = blocked) -> size -> throttle -> transport with an idempotency key. Every message carries `List-Unsubscribe` (https one-click) and `List-Unsubscribe-Post`, a visible unsubscribe line and the tenant footer. A provider/SMTP refusal of the recipient counts as a hard bounce and suppresses.
- Queueing: queued inbox email rows are sent by the `dispatch` stream (every 5 min); campaign sends go through `connector_sync` jobs `email.campaign` (splits into batches of 25, staggered to stay under 120/min) and `email.batch` (a throttled or transient batch re-queues only its unsent leads). Per-lead idempotency key plus provider-id dedupe on the stored message keep retries from double sending (SMTP has no provider-side dedupe: a crash between send and record can repeat one message).
- Webhooks: Resend (Svix `svix-id/-timestamp/-signature`, new verifier verify/svix.ts, tolerance 300 s, rotation-safe) via the T023 receiver. delivered/sent move the message forward only; hard bounce (Permanent) fails the message and suppresses; complaint suppresses AND withdraws marketing consent; Transient/Undetermined bounces and delays suppress nothing. Idempotent; a message id from another tenant is rejected. SMTP has no callbacks (stated on the page).
- Suppression list (`email_suppressions`, per workspace): hard bounces, complaints, unsubscribes, manual; shown on /settings/email (masked unless `pii.read`).
- Unsubscribe: signed, expiring token (HMAC, 180 days, carries tenant/workspace/connection/lead, never an address). Public page /unsubscribe/<token> (GET never writes, a button confirms) and RFC 8058 one-click POST /api/email/unsubscribe/<token>. Both write a `withdrawn` consent_log row (hashed subject, `marketing_email`) and the suppression row, emit `email.unsubscribed`, are idempotent and rate limited. Middleware lets /unsubscribe/ through without a session (one line).
- Mailchimp: OAuth (MAILCHIMP_CLIENT_ID/SECRET), data centre from the OAuth metadata (validated), audience chosen on /settings/email. Push of a segment (RLS-scoped lead ids, chunks of 50): only leads passing `can_contact` and not suppressed are sent, member status is `status_if_new` so an existing unsubscribe is never reversed, the segment name is the member tag. Pull every 30 min: unsubscribed -> consent withdrawal + suppression, cleaned -> hard-bounce suppression; the cursor only advances after a whole pass. Optional instant webhook (form body, `k` secret, generated on the page and shown once; other audiences ignored).
- Demo/showcase: mock transport (sandbox key `re_mock_key` / host `mock.smtp.invalid`, or APP_ENV=demo without credentials) never touches the network and is refused in production; labelled Showcase. Demo sessions never write; /settings/email renders sample data.
- Strings: `email` namespace (messages/{en,ta}/email.json, registered in src/i18n/registry.ts; Tamil is a short draft with `_review`), `email.sandbox` and `mailchimp.sandbox` in integrations.json. Env names added to .env.example, no values. Events: src/lib/events/catalog/email.ts. Permission catalogue only (`integrations.manage`, `messages.send_email` for the campaign action the integrator adds).
- One framework fix: `refreshIfNeeded` treated a connection with no recorded token expiry as expired and tried to refresh it (a Mailchimp token never expires, so the connection would flip to needs_attention). A token with no expiry now means nothing to refresh (core/lifecycle.ts, 2 lines).
Tests: unit src/lib/connectors/email/__tests__ (pure: merge escaping, token sign/expiry/tamper, suppression logic, MIME build and header injection; send: consent gating on every path incl. withdrawal after queueing, suppression, sender, merge, throttle, idempotency, isolation, template batches; webhook: Svix signature through the real receiver (tamper, wrong key, stale, rotation), parsing, effects, replays, tenant isolation; transport: Resend client, SMTP session over a scripted server, DNS check, selection; unsubscribe-apply) and src/lib/connectors/mailchimp/__tests__ (mapping, consented-only push through the real runner, pull and cursor, webhook). Cypress written, NOT run: connectors/email-send.cy.ts, connectors/mailchimp-sync.cy.ts, connectors/unsubscribe-consent.cy.ts. typecheck, lint and Vitest only; no build, no browser.
Deviations from plan:
- The Resend webhook signing secret is entered on /settings/email after connecting (Resend only shows it once the webhook, which needs the connection id, exists); the connect form takes the API key only.
- Resend template/subject: `message_templates.subject` and `messages.subject` are optional columns (backlog); without them the subject is read from a `Subject: ...` first line, else "Message from <sender name>".
- No UI to compose or send from the inbox/lead page (those files are not in Owns): the pipeline, the dispatcher and `enqueueEmailCampaign` are ready; see Needs.
- Mailchimp push consent: the framework gate (`can_contact` via runPush) plus the suppression check; there is no Mailchimp-side consent field mapping beyond subscribed status.
Needs from integrator: SQL under "T038 needs" in docs/migrations-backlog.md; env EMAIL_UNSUBSCRIBE_SECRET + APP_BASE_URL (sending is blocked without them); connector_availability rows for resend, email-smtp, mailchimp; `channelFor("email")` live in inbox/_lib/channel.ts and a send action calling the queued-row path; a campaign server action calling `enqueueEmailCampaign` behind `messages.send_email`; `setEmailSender(platformEmailSender(process.env))` for system mail; Mailchimp OAuth app (client id/secret); nav entry for /settings/email.
Owner decisions: unsubscribe link lifetime (180 days) and whether a hard bounce should also withdraw consent (currently suppression only); whether complaints should block the lead across all workspaces of the tenant (currently per workspace); the footer (business name and postal address) is the tenant's responsibility, nothing enforces it.
Known gaps: nothing ran against real Supabase, Resend, SMTP, Mailchimp or a browser. The Supabase store is not unit-tested (fake store only). The suppression table does not exist until the backlog SQL is applied (reads as empty with a warning). Mailchimp audience list is fetched on each page load. SMTP port 465 is assumed implicit TLS, every other port requires STARTTLS.

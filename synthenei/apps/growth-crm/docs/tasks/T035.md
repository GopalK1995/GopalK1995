Done:
- Connector `whatsapp` (src/lib/connectors/whatsapp/**, registered in connectors/all.ts). Manual connection through the generic connect form: WABA id, phone number id, system-user token, Meta app secret (verified with one Graph call, then stored in the encrypted Vault by the framework lifecycle; the app secret doubles as the webhook signing secret). Embedded signup server half (`embedded.ts`: code exchange with the platform app from env, app subscription, same credential bundle); the browser popup is not built (no UI path in Owns).
- Inbound: signed webhook (X-Hub-Signature-256, T023 receiver) -> `connector.webhook.handle`: text, image, audio, video, document, sticker, location, contacts, button and list replies; reactions ignored; unknown types stored as a bracket token. A new number becomes a lead (source whatsapp; click-to-WhatsApp referral -> utm campaign + ctwa_clid), conversation per (workspace, wa_id), message dedupe by wamid (idempotent, tenant scoped), `last_inbound_at` only moves forward, a closed conversation reopens. Media bytes go to the private `wa-media` bucket by reference (path on the message, never a URL); a failed download keeps the message.
- STOP / unsubscribe / opt out (plus Tamil and Hindi keywords): whole-message match only; writes a `withdrawn` consent_log row (hashed subject, lead id when known), so `can_contact` blocks every later send including queued ones; idempotent; no lead is created for a STOP-only message. Optional connection setting `inbound_implies_optin` (default off) records a grant when a customer messages first, never over a withdrawal.
- Status callbacks sent / delivered / read / failed: rank rule (never backwards), vendor error code kept, `message.status` event. The template status webhook updates the stored template.
- Outbound: the dispatcher takes the inbox's `queued` messages (T028 path) and sends. Gates, each failing closed and visible on the message: lead linked, `can_contact('whatsapp')` re-checked at send time, recipient, throttle (600/min/number, in-memory, retried later), an approved template with parameters recovered from the rendered body (exact vendor language kept) OR free text only inside the 24 h window (else status `pending_template`). Vendor refusals keep their code (window 131047, sandbox test recipient 131030; throttles are retried). A dead token = needs_attention.
- Template sync (every 6 h): Meta templates -> message_templates (en and ta; other languages skipped and counted), status mapping, rejected reason, name clashes skipped.
- Tenant isolation: events are processed only when their phone_number_id equals the one in THIS connection's credentials; `wa_numbers` registration refuses a number owned by another workspace; every store query is tenant/workspace scoped.
- Sandbox / showcase: the mock gateway (token `wa-mock-token`, or APP_ENV=demo without credentials) never touches the network, models Meta's 5-recipient test limit and is refused in production. Real calls only with real credentials; `WHATSAPP_API_BASE` points the Graph client at a stub.
- Strings: `messages/{en,ta}/whatsapp.json` (namespace `whatsapp` registered in src/i18n/registry.ts; Tamil is a short draft) and `whatsapp.sandbox` in integrations.json. Env names added to .env.example, no values.
Tests: unit src/lib/connectors/whatsapp/__tests__ (pure, signature, inbound, outbound, graph): payload fixtures for text, image, audio, document, location, reply, reaction, referral, statuses, template status and garbage; signature accept, tamper, wrong secret, missing header and duplicate through the real receiver; window rule (boundary, no inbound, IST offsets); STOP; dedupe; status ordering; isolation; template parameter recovery; sandbox recipient limit; Graph client (bodies, retries, error mapping, paging, size cap); embedded signup. Cypress written, NOT run: connectors/whatsapp-inbound.cy.ts, connectors/whatsapp-send-sandbox.cy.ts. typecheck, lint and Vitest only; no build, no browser.

- No UI built (not in Owns): the generic connect form renders the credential fields; there is no embedded-signup button, template list, per-message failure display or webhook-URL helper. The strings for them exist in the `whatsapp` namespace.
- Template variables are recovered by matching the rendered body against the template (the inbox does not store them). A body edited after rendering is blocked as `template_params`, never sent with guessed values.
- messages.attachments / error_code / error_detail and the unique indexes are in docs/migrations-backlog.md ("T035 needs"); until applied, media references and failure codes are not persisted (writes retry without the columns) and wamid dedupe relies on the pre-insert check.

- Per-message pricing: a note in the whatsapp namespace (Meta bills by template category; no prices in code); the status callback's pricing category is carried on the `message.status` event; no cost is calculated.

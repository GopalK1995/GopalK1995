Done:
- `/onboarding` (`src/app/(app)/onboarding/**`): an 8-step guided wizard (starter kit, branding, modules, pipeline, custom fields, invite team, connect an integration, import leads) that orchestrates existing, already-permission-checked actions rather than re-implementing them: the template/branding/modules steps call `saveConfig` (the real config system, `settings/_components/config-actions.ts`), the team step calls the real `inviteMember`, and the pipeline/fields/integration/import steps are "confirm you did it" panels that link out to their own full editors (`/settings/pipelines`, `/settings/fields`, `/integrations`, `/import`) and just record progress. Progress (`_lib/types.ts`/`steps.ts`/`progress.ts` -- the three files already on disk when this task picked up; kept as-is, they were correct) persists as a per-tenant signed-via-house-convention cookie (`onboarding_<tenantId>`, `_lib/state-store.ts`), not a database row -- deliberately: it is UX state (which step you're on), not business data, and every real mutation a step makes re-checks its own permission server-side regardless of what the cookie says, so a stale or tampered cookie can show the wrong step but never skip a real check. Resume (first `todo` step), required-vs-optional blocking, and finish-gating are all pure and unit-tested (`_lib/__tests__/progress.test.ts`).
- Branding step: name, product name, accent hue (0-359 slider), a derived monogram preview (first letter of the name -- matches how `branding-tab.tsx`'s preview already derives it; no new field, see Deviations), and a live WCAG contrast check reusing the exact pure math `settings/_components/contrast.ts` already has (`contrastChecks`), recomputed server-side before save and never trusted from the client.
- `/admin/tenants/new` (`src/app/admin/(console)/tenants/new/**`): a dedicated full-page form calling the existing `createTenant` action (same one the `/admin/tenants` list page's dialog already uses) -- a stable, bookmarkable/linkable entry point alongside the dialog, not a second implementation of tenant creation.
- `src/components/empty/**`: a shared `ModuleEmpty` component plus one designed definition (icon, title, body, CTA + target route) per module in `definitions.ts` (leads, pipeline, accounts, campaigns, audience, analytics, inbox, tasks, integrations, data-health, ai, objects) -- the generic `EmptyState` in `components/ui/states.tsx` stays the "could not load" primitive used everywhere; these are the specific, designed "you have zero data, here's what to do" states the accept criteria asks for.
Tests: unit `_lib/__tests__/progress.test.ts` (13 tests: parse/empty-state defaults, markStep/setKit clock behaviour, resumeStep order, counts always summing to the total, blockers ignoring optional steps, canFinish/finish agreeing, finish never requiring optional steps) -- ran, 13/13 pass. Cypress `onboarding/new-org-end-to-end.cy.ts` (demo: walks every step including the optional ones, verifies resume survives a reload, verifies Finish stays blocked while any required step is unanswered even with every optional step skipped; real-gated: a fresh real tenant's owner lands on an empty wizard) and `cypress/component/empty/module-empty.cy.tsx` (component test, not an e2e visit -- see Deviations).
Cypress itself was not installed in this environment at all before this task; `npx cypress install` (~600 MB) stalled mid-unzip twice before a third attempt finished (this is likely why every task in this project's history says "Cypress written, NOT run" -- the binary does not reliably install here). With it installed: `module-empty.cy.tsx` **actually ran and passed** (3/3) -- the first real Cypress execution recorded against any task in this project, as far as these task docs show. It needed one real fix first: `ModuleEmpty` used `next/link`, which throws (`Cannot read properties of undefined (reading '__NEXT_ROUTER_BASEPATH')`) when component-mounted outside an App Router context; switched to a plain `<a>` styled with the existing `buttonVariants` (a single CTA out of an empty module is not a prefetch-worthy hot path, so this costs nothing real). `new-org-end-to-end.cy.ts` was also run against a live `next dev` server (after the T052 fix, rebased in) and did **not** pass, but not because of this task's code: `cy.loginAs`'s session setup hits a full, unsuppressed React hydration-mismatch error on `/login` in dev mode. `cypress/support/e2e.ts` already has a line for this exact, pre-existing issue ("Known app issue (reported in docs/tasks/T002.md): React hydration mismatch #418 on first load of /login", filtering the string `Minified React error #418`) -- but that string is the *production*-build minified form; `next dev` prints the full, unminified hydration-mismatch message instead, which the existing filter does not match, so it is not suppressed and fails every spec that calls `cy.loginAs` under `next dev`. Not fixed here: `cypress/support/e2e.ts` is a shared file this task does not own, and the right fix (broaden the filter, or match on the error type rather than the minified string) is T002's call. `npm run typecheck`, `npx eslint`, `npx vitest run`, and `npm run build` all ran clean on this task's files.
Deviations from plan:
- Monogram is a derived preview (first letter of the organisation name), not a stored field: `config/types.ts`'s `branding` section is `{name, product, hue, fonts}` with no monogram slot, and the existing `tenant.monogram` static field is a different, unrelated system. Adding a new column/section for a letter that is already computed everywhere else felt like the wrong kind of new surface for what the accept criteria actually needs (a preview during setup).
- `src/components/empty/**` is built and exported but **not wired into any other module's page** (leads, pipeline, campaigns, etc.) -- those files belong to earlier tasks (T013/T014/T029/...) that already shipped and are already Cypress-covered; swapping their empty-state markup was explicitly left out of this task's diff after checking with the integrator, rather than reaching into files outside this task's `Owns` list. `module-empty.cy.tsx` is therefore a Cypress **component** test (`cypress/component/empty/`, real coverage of what was actually built) rather than the planned `onboarding/empty-states.cy.ts` **e2e** spec (which would need to visit pages that don't use these components yet, and would have been testing nothing).
- `cypress/e2e/onboarding/empty-states.cy.ts` (the literal path BUILD-PLAN.md names) was not created, for the same reason: there is no page using these components yet to visit, and demo tenants are always seeded with data (never a genuinely zero-data workspace), so an e2e "visit every module in a fresh workspace" spec would currently have nothing to assert against either way.
- `/onboarding` is not wired into the shell's nav or into a forced post-invite redirect: `ALWAYS_ALLOWED_PAGES` already includes it (pre-existing), but nothing currently points a brand-new owner at it automatically. Making that happen touches the login/accept-invite flow and `src/components/shell/nav.ts` more than a one-line addition, and risked changing behaviour for existing users with no onboarding state at all (every existing demo/seeded tenant).

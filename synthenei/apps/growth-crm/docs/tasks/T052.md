## Built
- **Public request form** `/privacy/<workspace slug>` (route group `(public)`, one line in `src/middleware.ts` makes `/privacy/` public). Tenant-branded notice built from the tenant row and `tenant_config.config.privacy` (no tenant names in code; generic wording in `messages/en/privacy.json`). Request kinds: access, correction, erasure, withdrawal, grievance.
- **Rate limit + email verification** (`src/lib/privacy/intake.ts`): per IP 5/h, per address 3/h, per workspace 200/h; a sealed AES-GCM link (`token.ts`, key `PRIVACY_VERIFY_SECRET`) is mailed to the address; nothing is stored until the person presses Confirm on the link page (GET never writes). The answer is identical for known and unknown addresses; honeypot field; the form says "unavailable" when the secret or the platform mail sender is missing instead of pretending. `privacy_requests` stores only the sha256 of the address (same recipe as the unsubscribe flow), one row per matching lead (or one with no lead).
- **Withdrawal** is applied on confirmation: `consent_log` rows (`withdrawn`, `captured_via = request`, notice version from config), lead consent flags cleared, unsubscribe list entry; the request is created already completed. Replays add nothing.
- **Owner inbox** `/settings/privacy` (+ `[id]` detail): due dates with text and icon (overdue / due soon / on track / closed), sorted by urgency, status moves with notes (closed stays closed, register never deleted), link a record by hand, per-kind panel.
- **Access export** `/settings/privacy/[id]/export` (GET): JSON bundle (`bundle.ts`) of lead, activities, conversations and messages, consent log, web events, tasks, deals, payments, calendar entries, contact, linked custom-object records, prior requests. Built on the owner's client (RLS), audited before it is served, `no-store`, a manifest lists every section and flags any that could not be read.
- **Correction**: the owner fixes the record, then completes the request with a note of what changed.
- **Erasure job** (`erasure.ts`, action `completeErasure`): owner only (also enforced by `erase_lead`), never in a support session. Order: audit "started" (failure aborts), read facts, **`erase_lead` on the owner's client**, then extension on the service client scoped by workspace: linked contact(s), custom-object records (only fields flagged `is_pii`), embeddings (the only rows deleted), calendar entries, reviews quoting the exact name, external links (reported as "erase at the source", links kept so a sync cannot recreate the person), payments and the unsubscribe entry (kept, stated), social/metric tables (counts only, nothing to erase). Every step is reported and written to the request notes; a failed step leaves the request in progress.
- **Consent capture** by a team member (`consent.ts`): append-only `consent_log` row with the notice version plus the lead flag.
- **Retention job** (`retention.ts`, `job.ts`, kind `privacy.retention` on the maintenance queue): rules from `retention_policies`; **soft delete first** (`deleted_at`) for leads and custom-object records, in-place clearing of personal fields otherwise; activities, messages and web events are cleared, never deleted. Dry run is the default mode; bounded batches and deadline. `privacy.purge` calls `public.privacy_purge` (backlog) to remove what was soft deleted 90+ days ago. **Both scheduled rows ship disabled**; the retention page shows the real job state (On / Off / Unknown).
- **Breach register** `/settings/privacy/breaches` (owners only): incidents, severity, data categories, people affected, 72 hour Board report clock, Board/people notified marks. Needs the new table (backlog); shows a setup state until then.
- **Audit events**: `privacy.request_status`, `privacy.request_note`, `privacy.request_linked`, `privacy.erasure_started`, `privacy.erasure_completed`, `privacy.access_export`, `privacy.consent_captured`, `privacy.retention_rule_saved`, `privacy.retention_rule_removed`, `privacy.retention_plan_run`, `privacy.breach_recorded`, `privacy.breach_updated`. Ids and counts only, never names or addresses.
- Registrations (one line each): middleware public path, `PAGE_PERMISSION["/settings/privacy"] = privacy.fulfil`, nav item, `handlers/index.ts` import, `PrivacyHubLink` on the legacy Settings > Consent & privacy tab, `PRIVACY_VERIFY_SECRET` in `.env.example`. `EraseButton` (still used by that tab) now calls the new action.

T053 · Platform billing and entitlement enforcement · MERGED (sha in final message)
Done:
- Plans, subscriptions and invoices for Synthan's own billing (`src/lib/billing/**`), distinct from the tenant-payments connector (`connectors/razorpay`): own types, config, store port, in-memory fake (also the Vitest fixture), Supabase adapter and a pure `service.ts` with no network or DB imports (dependency-injected store/env/clock/audit/fetch).
- Entitlement enforcement: `orgState` derives `ok` / `readonly` / `suspended` from tenant status, trial end, cancellation and past_due + grace days; `seatLimit`/`seatStatus` combine the plan limit with purchased seats; `applyBilling` folds both into the authz `Principal` (`suspended` -> `tenant.status=suspended`, `readonly` -> an already-expired trial marker, seats-full -> `members.invite` capped) and only ever tightens, never loosens, an already-suspended principal. Wired into `loadPrincipal` for real sessions only (`withBilling`, 10 s per-tenant cache, infra failures leave the principal unchanged so a billing outage never locks everyone out). Demo sessions build the principal from the tenancy fixture and never call `withBilling`: billing enforcement is a real-session-only feature by design, same as every other authz source in `loadPrincipal`.
- Razorpay Subscriptions in test mode: `razorpayConfig` refuses a live key unless `BILLING_RAZORPAY_LIVE=1`, refuses a test key with the flag set, and is picky about the `rzp_(test|live)_` key shape. `startSubscription` creates the Razorpay plan on first use (cached on the plan row), creates the subscription, records the pending provider id; the webhook (`handleWebhook`, HMAC-SHA256 signature, timing-safe compare) is what actually flips status to active and swaps the plan, so an abandoned checkout never silently activates anything. `subscription.charged` writes exactly one paid invoice per billing period (keyed by tenant+period, redelivery-safe).
- GST invoices: integer-paise maths (`gst.ts`), CGST+SGST for an intra-state supply (buyer state = seller state), IGST otherwise; the odd paise goes to SGST. PDF rendering (`pdf.ts`) and a manual-invoice path (`createManualInvoice`/`setInvoiceStatus`) for pilots invoiced outside Razorpay, with a one-way status machine (draft -> issued/void -> paid/void; void is final).
- Owner UI (`/settings/billing`): plan, seats meter, trial/past-due/cancelled/suspended banners, GST details form, invoice list (PDF hidden for drafts and in demo), self-service subscribe/cancel. `billing.manage` is denied once read-only, except the owner can still act on `org_readonly` specifically so they can pay their way out; a suspended organisation stays blocked. Demo sessions short-circuit subscribe/cancel/save-details before they reach Razorpay or the store mutation that matters, and say so (`demoNotice`).
- Platform admin UI (`/admin/billing`, `platform.billing` to edit, `platform.read` to view): subscriptions table with read-only/suspended badges, per-tenant edit (plan, status, seats, trial end, period end, reason — reason is required and kept on the audit line), plan catalogue CRUD, manual invoices and status transitions. Unlike tenant-status suspend/reactivate (`setTenantStatus`), every billing admin action runs for real even in a demo session (against the shared in-process memory store), which is what makes the Cypress specs below possible without a database.
- Nav entries gated on `billing.read` (owner) / always-visible for platform roles; `PAGE_PERMISSION["/settings/billing"] = "billing.read"`.
- Strings: `billing` namespace (`messages/en/billing.json`; no Tamil file — not reviewed yet, same gap as other recent namespaces).
Tests: unit `src/lib/billing/__tests__/` — `state.test.ts` (orgState every branch incl. trial/cancelled/past_due + grace, seat maths, applyBilling never loosening), `gst.test.ts` (intra/inter split incl. the odd-paise case, place of supply, INR formatting, rupee parsing), `config.test.ts` (issuer/razorpay/grace-days config parsing and refusal reasons), `razorpay.test.ts` (webhook HMAC verify, event mapping), `service.test.ts` (every use-case against the in-memory store and a mocked `fetch`: start/cancel/webhook incl. redelivery idempotency and unknown-subscription handling, manual invoices and status transitions, invoice PDF scoping, admin subscription/plan edits) — 58 tests, all against the same in-memory store the demo UI uses. Cypress `billing/seat-limit.cy.ts`, `billing/trial-expired-readonly.cy.ts`, `billing/subscription-test-mode.cy.ts` (demo-mode, run against the shared in-process store via the admin console) and `billing/suspended.cy.ts` (real session only — see Known gaps). Deviations from plan:
- `suspended` is a tenant-level status (`setTenantStatus`), not a subscription field, and the demo build of that action only reports what it "would" do — it never mutates the fixture tenants. So, unlike the other three specs, `suspended.cy.ts` cannot be driven through demo data at all; it is gated on real credentials (`CYPRESS_REAL_SUPER_EMAIL`/`_PASSWORD`, `CYPRESS_QA_SUSPEND_TENANT_SLUG`, and the existing `CYPRESS_QA_OWNER_EMAIL`/`_PASSWORD` from `cypress/e2e/settings/_helpers.ts`) and skips cleanly without them, same convention as `cypress/e2e/audit/export-blocked-in-support.cy.ts`.
- `subscription-test-mode.cy.ts`'s demo test proves the opposite of what its name suggests on a fresh checkout: with no `RAZORPAY_KEY_ID` configured, subscribing is a safe no-op that never reaches Razorpay. The real Razorpay-returns-a-checkout-url assertion is a separate `it`, gated on test keys being configured server-side plus owner credentials.
Needs from integrator: env vars (named in `.env.example`, no values here) `BILLING_GSTIN`, `BILLING_SAC_CODE`, `BILLING_GST_RATE_PERCENT`, `BILLING_LEGAL_NAME`, `BILLING_ADDRESS` (pipe-separated lines), `BILLING_PAST_DUE_GRACE_DAYS`, `RAZORPAY_KEY_ID`/`_KEY_SECRET`/`_WEBHOOK_SECRET` (test keys only until KYC), `BILLING_RAZORPAY_LIVE`; the plans, subscriptions and invoices tables/migration (this task assumed the schema the store ports already target — confirm against the current `supabase/migrations` state before go-live); a `connector_availability`-style row is not needed here (this is platform billing, not a tenant connector); for `suspended.cy.ts` and the real half of `subscription-test-mode.cy.ts`, a disposable staging tenant slug and the Cypress env vars named above.
Owner decisions: whether `BILLING_PAST_DUE_GRACE_DAYS` should have a platform-wide default rather than "never enforced" when unset; whether `members.invite` should be the only permission capped at the seat limit or others should join it later; Tamil translation of `billing.json` (currently English only, like several other recent namespaces).

# AUD-036 Meta lifecycle and AUD-028 honest sync status

Branch `fix/meta-lifecycle`. No migration applied, no Meta call made. Everything below that touches Graph behaviour is fixture tested only.

## AUD-036 (what changed)
- Token expiry: `healthStep` (daily) reads `debug_token` and stores `expires_at` in `integrations.token_expires_at` and both `expires_at` and `data_access_expires_at` in `integrations.health.meta`. `selectMetaAssets` does the same at connect time (the long-lived exchange did not return `expires_in` on the live row, which is why it was NULL). A connection inside 7 days of expiry makes the health run `partial` with reason `token_expiring_reconnect`, and the integration page shows "Needs attention".
- subscribePage: outcome stored in `health.meta.webhook` ({subscribed, error, at}); shown on the integration page; "Retry webhook subscription" action (`retryMetaWebhook`, audited as `meta.webhook_retry`). The chip stays "Connected" because polling metrics still work; the health line is the visible signal.
- OAuth state: single `DELETE ... WHERE state_hash AND expires_at > now() RETURNING`; only the caller that gets a row passes.
- Graph version: `META_GRAPH_API_VERSION` now drives the OAuth dialog URL, the token URL and API calls; a value not shaped `vNN.N` falls back to `v21.0`. OAuth URLs are resolved at module load (the ConnectorDef is a constant), so changing the env needs a redeploy.
- Health line on /integrations/meta-ads: permissions granted of requested (+ missing names), access expiry, webhook yes/no, last successful sync (last social or insights run that imported rows).

## AUD-028 (what changed)
- `SyncResult` may carry `status: skipped | partial | no_data` and `reason`. Runner stores `skipped` (never success, does not touch last_sync_at), `partial` for early stops, and `success` + "No data: reason" for empty answers. Stale `running` rows older than 15 min are closed as `failed` before each run (reaper).
- Zero-row Ads insights, the 15-minute dispatcher with no Instagram account, "up to date" and "checked today" are no longer silent successes.
- Social: account status can be `no_data`. Facebook with 0 followers and 0 posts, or any account with no feed/reel/video post, is `no_data`, not `ok`. A refused account metric is `partial` with its Graph code (`follower_count:100`), shown on /analytics/social.

## Diagnosis: missing feed/reel posts and empty account metrics (evidence: public.sync_runs, social_posts, social_accounts, read-only)
Evidence: 6 latest social runs are all `success`, rows 4/0, sample `instagram posts 2 metrics 2, facebook 0 0`; `social_posts` holds only 2 `story` rows; `social_account_metrics_daily` has 0 rows; both accounts `last_sync_status = ok`, IG followers 572, FB followers 0.

1. Account metrics empty (confidence HIGH on the mechanism, MEDIUM on which metric Meta rejects). The old call asked `reach,profile_views,website_clicks,follower_count` in one request with `period=day`. Instagram requires `metric_type=total_value` for `profile_views` and `website_clicks`, and mixing them with time-series metrics makes Graph answer code 100 for the whole request. `noData()` swallowed code 100 and returned `[]`, the sync wrote zero rows and still marked the account `ok`. Fixed: separate calls per metric group, `metric_type=total_value` per day for the two total metrics, errors reported with the Graph code, and today's follower count always stored from the profile call (so the follower trend is never empty while the account has followers).
2. Feed posts and reels missing (confidence MEDIUM-HIGH, two code defects, one possible data cause). (a) The incremental cut-off came from the newest stored post of ANY kind. Once a story was stored (2 stories, 25 Nov), `since` moved to "yesterday" and every older feed post or reel was never requested again. Fixed: stories are excluded from the cut-off. (b) The first run only reached back 30 days and passed `since` to the Instagram `/media` edge, where time filtering is not reliable. If the account has no feed or reel posts in the last 30 days (plausible for a small account) the first run legitimately got none. Fixed: first run reaches back 120 days, no `since` on IG `/media`, the sync filters and stops paging client side. (c) Not provable without a real run: the account may genuinely have no posts, or Meta may require the connected token to be the Instagram-linked Page's token. The run now says `no_posts_returned` instead of `ok`.
3. Facebook followers 0 / 0 posts: could be a real new Page, or the new Pages experience where `followers_count`/`published_posts` return nothing for the page token. Now `no_data`; UNVERIFIED which.
